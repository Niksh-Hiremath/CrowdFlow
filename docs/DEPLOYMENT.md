# Hugging Face CPU Space deployment

The production topology is one public Hugging Face **Docker Space** running the built Vite client and Express API in the same Node.js process. It is CPU-only: simulation runs locally in Node, while OpenAI inference is an outbound API call. The container listens on `0.0.0.0:7860`.

Deployment remains pending only until an authorized Team-organization owner is selected.

## Space configuration

In the signed-in browser, choose **New Space**, an eligible owner, **Public**, **Docker**, and **CPU Basic**. Preserve or add this YAML front matter at the very top of the Space repository's `README.md`:

```yaml
---
title: CrowdFlow
emoji: "🚦"
colorFrom: teal
colorTo: indigo
sdk: docker
app_port: 7860
pinned: false
---
```

Push the repository contents, including the root `Dockerfile`, to the Space. Do not blindly replace a README generated by the creation form: retain its YAML front matter. The multi-stage image builds the Vite client and Express server, removes development dependencies, runs as a non-root user, and exposes an image health check at `/api/health`.

## Safest publish flow

Because the current MCP credential is read-only, create the Space and configure its secret in the browser. For the code upload, use a separately cloned Space repository rather than adding a remote to the working repository; this avoids publishing unrelated history or files. Authenticate that clone with an SSH key registered in Hugging Face, or with a separately created fine-grained write token. Never reuse, expose, or copy the MCP OAuth credential.

Before committing in the separate clone, confirm that no `.env*` file was copied and that the Space README metadata remains intact. An installable alternative is the current `hf` CLI (`hf repos create`, `hf upload`, and `hf spaces secrets add`) authenticated with a write-scoped token, but the CLI is not presently installed on this machine. The browser plus a separate Git clone requires no additional local tooling beyond Git and OpenSSH.

## Secret configuration

In **Space Settings -> Variables and secrets**, add `OPENAI_TOKEN` as a **Secret**, never as a public variable, Docker build argument, committed file, or log value. Paste it manually; deployment tooling should not read or print the local `.env`. The server accesses it only as `process.env.OPENAI_TOKEN` and sends OpenAI requests with the exact model `gpt-5.6-terra`.

If the secret is absent, the application remains demoable: venue extraction returns an editable deterministic template and advice is derived deterministically from the validated `FindingBundle`.

For local development, keep the token in the existing untracked `.env`. The Docker build context excludes all `.env*` files at every directory depth.

## Runtime expectations

- Keep the MVP at one Space replica/process. Sessions and live simulation state are in memory, and WebSocket clients are attached to that process.
- CPU Space disk is disposable. A rebuild, restart, or sleep/wake cycle clears in-memory sessions and any unmounted local files.
- If multiple replicas are introduced later, move session/simulation state to an external store and add pub/sub for WebSocket fan-out; otherwise clients can reconnect to a replica that does not own their session.
- Serve the browser client and API from the same origin. This avoids CORS configuration and lets WebSocket upgrades follow the Space's public HTTPS origin (`wss://`).
- Bound simulation tick work and batch WebSocket updates. OpenAI calls should stay outside the tick loop and run only for extraction or explicit advice requests.
- Do not write uploads permanently. Process them in memory, apply request-size limits, and discard buffers after extraction.

## Release checks

Run these checks before uploading:

```bash
npm ci
npm run typecheck
npm test
npm run build
docker build -t crowdflow-ops .
docker run --rm -p 7860:7860 crowdflow-ops
```

The no-secret container run is deliberate: it verifies the public image and deterministic fallback without loading the local `.env`. Then verify:

1. `GET /api/health` succeeds on port 7860 and reports `aiConfigured: false` for that smoke run.
2. The built client loads from `/` and API requests remain same-origin.
3. Docker reports the container as healthy.
4. Live WebSocket snapshots update after a confirmed session starts.
5. Missing-token mode returns deterministic fallbacks without exposing a credential or raw provider error.
6. Space logs never contain request images, full FindingBundles, or secret values.

After deployment, expect a cold start whenever free CPU Basic sleeps after inactivity. Open the Space before a demo and recreate a session after a restart.
